# 41 张表如何分 7 个领域

## 领域划分总览

ARCH ACG 的数据库共 41 张表，按业务领域分成 7 组：

| 领域 | 表数量 | 核心表 |
|------|--------|--------|
| 用户 | 3 | users, user_settings, user_follows |
| 内容 | 12 | posts, post_media, post_comments, post_likes, works, work_media... |
| 交易 | 6 | commissions, commission_applications, wallets, transactions... |
| 服务者 | 10 | service_providers, photographer_profiles, coser_profiles... |
| 通信 | 3 | conversations, messages, notifications |
| 平台 | 7 | categories, exhibitions, exhibition_booths, reports... |
| 系统 | 3 | system_configs, audit_logs, admins |

## 内容领域最复杂：12 张表

内容是社交平台的核心，也是表最多的地方：

```
posts（动态）
├── post_media（媒体附件，一对多）
├── post_comments（评论，支持 replyToId 嵌套）
├── post_likes（点赞）
└── comment_likes（评论点赞）

works（作品集）
├── work_media（作品图片/视频）
├── work_likes（作品点赞）
└── work_bookmarks（作品收藏）
```

动态和作品集是两个独立的内容模型。动态是时间线流式的内容，作品集是创作者的精选展示。

评论表的 `reply_to_id` 字段支持嵌套回复（楼中楼），但 v1.0 只实现了平铺评论，后续再做嵌套展开。

## 交易领域：约单闭环

```
commissions（约单需求）
├── commission_applications（服务者申请）
└── commission_reviews（完成后评价）

wallets（钱包）
└── transactions（交易记录）
```

交易领域预留了钱包和交易表，但 v1.0 还没有接入支付。后续计划对接支付宝/微信支付，实现担保交易闭环。

## 服务者领域：10 张表对应 6 类服务者

每种服务者有自己的 profile 表，存储差异化字段：

| 表 | 服务者类型 | 特有字段 |
|----|----------|---------|
| photographer_profiles | 摄影师 | 器材、风格、可拍场地 |
| coser_profiles | COSER | 可出角色、身高体重 |
| makeup_profiles | 妆娘 | 擅长妆面、作品集 |
| wig_profiles | 毛娘 | 擅长发型、接发经验 |
| costume_profiles | 服装师 | 尺码范围、制作周期 |
| prop_profiles | 道具师 | 擅长材质、制作周期 |

加上公共的 `service_providers` 表做统一管理，以及 `service_portfolios`（作品集）、`service_tags`（标签）、`service_reviews`（评价）、`service_availability`（档期）。

## 设计约定

全部表统一遵循以下约定：

- 编码：`utf8mb4`，支持 emoji
- 主键：`BIGINT UNSIGNED AUTO_INCREMENT`
- 时间：`DATETIME`，每张表都有 `created_at` 和 `updated_at`
- 删除：软删除字段 `deleted_at`
- 外键：级联删除，保证数据一致性
- 灵活字段：`JSON` 类型存储可变结构数据

## 后续优化

- [ ] 按时间分表（动态、消息等高频写入表）
- [ ] 读写分离（主库写、从库读）
- [ ] 冷数据归档（超过 1 年的动态归档到历史库）

## 小结

41 张表听着多，但按领域拆开后每个领域 3-12 张，逻辑清晰。关键是领域边界要画好——内容、交易、服务者、通信各管各的，不要交叉依赖。后续加功能时也是在对应领域内加表，不会破坏整体结构。

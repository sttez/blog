# 四层架构设计与数据流

## 整体架构

ARCH ACG 采用经典的四层架构：

```
用户层 → 网关层 → 服务层 → 数据层
```

| 层级 | 技术 | 职责 |
|------|------|------|
| 用户层 | React 19 SPA | UI 渲染、交互、路由 |
| 网关层 | Nginx | 反向代理、SSL、静态资源、WebSocket 代理 |
| 服务层 | Spring Boot 3.2 | 业务逻辑、认证、9 个模块 |
| 数据层 | MySQL + Redis + MinIO | 持久化、缓存、文件存储 |

## 前端端口分配

主站跑在 `5173`，后台管理跑在 `5174`，开发时通过 Vite proxy 代理 API 请求到后端 `8080` 端口，避免跨域问题。

## 后端 9 个模块

```
arch-acg-backend
├── auth          # 认证（登录/注册/Token）
├── content       # 内容（动态/作品/评论）
├── commissions   # 约单
├── search        # 搜索
├── upload        # 文件上传
├── notifications # 通知
├── service-providers  # 服务者管理
├── comments      # 评论
└── moderation    # 内容审核
```

每个模块遵循四层分层：Controller → Service → Mapper → Entity。Controller 只做参数校验，不含业务逻辑（后面单独写一篇）。

## 缓存策略

Redis 在项目中承担了五个关键角色，每个都选了不同的数据结构和 TTL：

| 场景 | 数据结构 | TTL | 说明 |
|------|----------|-----|------|
| Token 黑名单 | String | Token 剩余有效期 | 登出后 token 失效 |
| 点赞状态 | Set | 永久 | Lua 脚本保证原子性 |
| 热门内容排序 | ZSet | 5 分钟 | 按热度分数排序 |
| 验证码 | String | 5 分钟 | 登录/注册校验 |
| 接口限流 | String | 滑动窗口 | 60 次/分钟，10 次/秒 |

## 安全链

请求进入后端的路径：

```
请求 → CORS Filter → JWT Filter → Authorization Filter → Controller
```

- **CORS Filter**：只放行白名单域名
- **JWT Filter**：从 Header 提取 token，验证签名和过期时间
- **Authorization Filter**：检查当前用户是否有权限访问目标接口
- **Controller**：处理业务逻辑

## 数据流示例：用户点赞

```
1. 前端 POST /api/v1/feed/{postId}/like
2. Nginx 转发到 Spring Boot
3. JWT Filter 验证 token
4. Controller 接收参数，调用 Service
5. Service 用 Lua 脚本在 Redis Set 中添加点赞记录（原子操作）
6. 异步更新 ZSet 热度分数
7. 返回成功
8. 前端更新 UI 状态
```

点赞不需要写数据库——全在 Redis 里完成，高性能。定时任务批量同步到 MySQL。

## 小结

四层架构不是什么新鲜东西，关键在于每一层的职责边界要清晰。Nginx 管流量分发，Spring Boot 管业务逻辑，MySQL 管持久化，Redis 管高频读写。各司其职，后续扩展也容易——比如加 Elasticsearch 做全文搜索，加 MQ 做异步消息。

# 技术选型：React 19 + Spring Boot 3.2 全栈方案

## 前端选型

### 为什么选 React 而不是 Vue

这是个人技术栈偏好的决定。React 19 引入的 `use()` hook 和 Server Components 方向让我觉得生态在持续进化。加上 TypeScript 的原生支持和 Zustand/React Query 等轻量状态管理方案的成熟，React 的组合式架构对复杂页面更友好。

### 核心依赖一览

| 技术 | 版本 | 用途 |
|------|------|------|
| React | 19 | UI 框架 |
| TypeScript | 6 | 类型安全 |
| Vite | 8 | 构建工具 |
| Tailwind CSS | 4 | 样式方案 |
| Zustand | 5 | 客户端状态 |
| React Query | 5 | 服务端状态 |
| React Router | 7 | 路由 |
| Framer Motion | 12 | 动画 |
| Lucide React | 1.11 | 图标库 |

### Zustand 而不是 Redux

Redux Toolkit 虽然比原生 Redux 好很多，但样板代码还是偏多。Zustand 的 API 极简——一个 `create()` 搞定 store，不需要 Provider 包裹，不需要 dispatch。对中小项目来说生产力更高。

### React Query 而不是自己封装

数据请求层我立了一条铁律：**不许用 useState + useEffect 做数据获取**。所有服务端数据走 React Query，统一处理 loading/error/缓存/重试/失效。这比手写 `useEffect` 加 `useState` 再手动管理 loading 状态强太多了。

## 后端选型

### 为什么选 Spring Boot

Java 21 LTS + Spring Boot 3.2 是一个成熟稳定的组合。虽然 Go 和 Node.js 在性能和开发速度上有优势，但 Spring 生态的完整性（安全、事务、缓存、定时任务、WebSocket）对于需要快速搭建完整后端的项目来说是最佳选择。

### MyBatis Plus 而不是 JPA

几个原因：

1. **SQL 可控**：复杂查询手写 SQL 比 JPA 的 JPQL 更直观
2. **国内生态**：MyBatis Plus 的 Wrapper 查询在国内用得非常普遍
3. **分页插件**：内置分页插件，一行代码搞定分页
4. **代码生成器**：Entity/Mapper/Service 可以自动生成

JPA 的自动建表和关联查询在简单场景下很方便，但一旦遇到复杂查询和性能调优，还是 SQL 更直接。

## 数据层选型

| 技术 | 用途 |
|------|------|
| MySQL 8.0 | 主数据库，41 张表 |
| Redis 7.0 | 缓存、限流、黑名单、热排序 |
| MinIO | 文件/图片存储 |

选 MinIO 而不是阿里云 OSS，主要是为了本地开发方便，部署时可以自由选择存储后端。

## 小结

技术选型没有绝对的对错，关键是**团队熟悉度**和**项目阶段匹配**。ARCH ACG 作为个人全栈项目，选了自己最熟悉的组合，同时在关键点上做了有意识的取舍（Zustand > Redux，MyBatis Plus > JPA，React Query > useEffect）。

# 光流提取的性能瓶颈与优化

## 问题

CASME2 数据集有 26 个被试，每个被试几十个微表情序列，每个序列几十到上百帧。逐帧提取 Farneback 光流的代码：

```python
for i in range(1, len(frames)):
    flow = cv2.calcOpticalFlowFarneback(
        prev_gray, curr_gray, None,
        0.5, 3, 15, 3, 5, 1.2, 0
    )
```

单次调用看着不慢，但乘以上万帧的总量，整个预处理跑完要好几个小时。而且中间不能断，断了就得重跑。

## 为什么这么慢

Farneback 算法本身计算量就大——它要在每个像素邻域做多项式展开和相位匹配。128×128 的图像还好，如果是原始分辨率（CASME2 部分帧是 640×480），速度会更慢。

更关键的是，Python 的 for 循环天然慢，每一帧都是一次独立的 OpenCV 调用，无法向量化。

## 解决方案

### 1. 缓存中间结果

最重要的优化：光流只算一次，结果存为 npz 文件。下次再跑预处理时，跳过已存在的文件：

```python
of_file = os.path.join(of_dir, f"{frame_id}.npz")
if not os.path.exists(of_file):
    flow = extract_optical_flow(prev_path, curr_path)
    if flow is not None:
        np.savez_compressed(of_file, flow=flow.astype(np.float16))
```

这样第一次跑完之后，后续只需要几秒钟就能完成（跳过已计算的光流）。

### 2. float16 压缩存储

光流的值域不大（Farneback 输出一般在 ±20 之间），用 float32 存储浪费空间。转成 float16 后文件体积减半：

```python
np.savez_compressed(of_file, flow=flow.astype(np.float16))
```

配合 npz 压缩，单个光流文件约 30KB。

### 3. 先 resize 再算光流

原始帧可能比 128×128 大，但模型输入只要 128×128。在算光流之前先 resize：

```python
prev = cv2.resize(prev, (128, 128))
curr = cv2.resize(curr, (128, 128))
flow = cv2.calcOpticalFlowFarneback(prev, curr, ...)
```

图像尺寸从 640×480 降到 128×128，计算量减少约 20 倍。

### 4. 关键点提取同步做

既然都要逐帧读取图像，不如把人脸检测、关键点提取、光流计算放在同一个循环里，避免重复 I/O：

```python
for i, fname in enumerate(frames):
    # 关键点提取
    lm = extract_face_landmarks(img_path, predictor, detector)
    save_landmarks(lm_file, lm)

    # 光流计算（与前一帧）
    if i > 0:
        flow = extract_optical_flow(frames[i-1], frames[i])
        save_optical_flow(of_file, flow)
```

一次遍历完成所有工作，I/O 开销只算一份。

## 实际效果

经过这四步优化：

| 优化前 | 优化后（首次） | 优化后（缓存命中） |
|--------|---------------|-------------------|
| ~4 小时 | ~1.5 小时 | ~10 秒 |

关键心得：对于数据预处理这种一次性任务，**缓存是王道**。与其花时间优化算法本身，不如把结果存下来避免重复计算。

## 推理时的光流

值得一提的是，推理时的光流是实时计算的，不存在缓存机会。好在推理时只需要算最近 32 帧之间的光流，每次只算 31 对帧，单帧延迟在可接受范围内。

# Superpowers + gstack：AI 编程的完美闭环

Claude Code 强大但危险 — 它写代码太快了，快到你来不及想清楚就堆出一堆半成品。这篇文章讲的是如何用两套 Skill 把 AI 的速度关进质量笼子里：

- **Superpowers（brainstorming）** = 你和 AI 之间的"想清楚再动手"机制
- **gstack** = 从方案到上线的全自动质量管线

两者配合，形成一个 **想法 → 设计 → 实现 → 审查 → 发布 → 复盘** 的闭环。

## ① 想法收敛：Superpowers /brainstorming

**核心问题：** AI 写代码不需要想清楚，但你需要。

很多人拿到 Claude Code 就直接说"帮我做一个 XXX 功能"，然后 AI 哗哗写出 500 行代码。问题来了：这 500 行可能方向就错了。

`/brainstorming` 是你和 AI 之间的 **需求澄清 + 设计收敛** 机制。它在任何代码之前强制运行，用铁律锁死：

> **在设计获批前，绝不能写任何代码。**

### 工作流程

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| 探索上下文 | AI 检查当前项目文件、文档、最近提交 | 对现状的共识 |
| 提出澄清问题 | 逐个问题，每次一个，理解目的/约束/成功标准 | 需求对齐 |
| 提出 2-3 种方案 | 带取舍分析和推荐理由 | 方案选择 |
| 呈现设计 | 按复杂度分节呈现，逐节确认 | 设计共识 |
| 写入设计文档 | 保存到 `docs/superpowers/specs/` 并提交 | 设计规范 (spec) |
| 自检 + 用户审查 | 检查占位符、矛盾、歧义、范围 | 可执行的 spec |

### 为什么它重要

- **防止"简单需求不需要设计"的陷阱** — 连做个 todo list 都要走这个流程，因为"简单"项目里未审视的假设最容易浪费工作量
- **大规模项目自动拆解** — 如果需求描述了多个独立子系统，brainstorming 会要求你先拆解再逐个设计
- **设计文档是可追溯的** — spec 文件被 git 管理，后续实现可以逐条对照

### 实际对话示例

```
你: "我想给博客加一个评论功能"

AI (brainstorming 启动):
  → 你希望用什么评论系统？Twikoo、Giscus 还是自建？
  → 评论需要哪些功能？嵌套回复？点赞？审核？
  → 对性能有什么要求？静态站怎么处理实时性？

  [经过 3-5 轮对话后]

  → 方案 A: Twikoo + 云函数（推荐，开箱即用）
  → 方案 B: Giscus + GitHub Discussions（开发者友好）
  → 方案 C: 自建 API + 数据库（完全控制但维护成本高）

  → 你选了 A，我来写设计文档...
  → spec 已保存到 docs/superpowers/specs/2026-05-10-twikoo-comments.md
  → 请审查一下，确认后我开始写实现计划
```

## ② 方案审查：gstack 四维评审

**核心问题：** 设计稿写好了，但你一个人的视角够吗？

设计方案通过 brainstorming 收敛后，不应该直接写代码。gstack 的方案审查阶段从四个不同视角审视同一个方案：

### /autoplan — 一键全维度审查

`/autoplan` 自动串联四轮审查，用 6 大决策原则自动决策，最后在审批门汇总需要人工判断的"品味决策"：

```
/autoplan 启动
  → CEO 视角 /plan-ceo-review    ← 产品方向对不对？范围该不该扩？
  → 工程视角 /plan-eng-review    ← 架构合理吗？边界情况想全了吗？
  → 设计视角 /plan-design-review ← 视觉体验能打几分？差距在哪？
  → DX 视角 /plan-devex-review   ← 开发者上手体验如何？
  → 审批门                        ← 汇总边界决策，人工拍板
```

### 各审查维度详解

| 审查 | 视角 | 核心问题 | 典型输出 |
|------|------|---------|---------|
| `/plan-ceo-review` | 创始人 | "这个产品有没有可能更好？该不该砍？该不该扩？" | 范围调整建议 |
| `/plan-eng-review` | 技术负责人 | "架构有没有坑？数据流通不通？测试覆盖够不够？" | 技术风险清单 |
| `/plan-design-review` | 设计师 | "每个设计维度 0-10 分，离 10 分差在哪？" | 设计改进 spec |
| `/plan-devex-review` | 开发者 | "新人拿到这个 SDK/工具，上手要多久？" | DX 摩擦点清单 |

### 为什么它重要

- **CEO 视角** 防止你在错误的方向上用力 — "用户真的需要这个吗？"
- **工程视角** 防止你写出上线就崩的代码 — "并发场景想过没？"
- **设计视角** 防止你的 UI 只是"能用"而非"好用" — "这个间距对吗？"
- **DX 视角** 防止你的工具只有你自己会用 — "新人 5 分钟能跑起来吗？"

## ③ 编码实现：Karpathy 准则 + gstack 安全兜底

**核心问题：** 代码写得快不等于写得好。

设计方案和审查都通过了，终于可以写代码了。但 AI 写代码有一个天然缺陷：它倾向于过度工程。

### Karpathy 四准则（自动生效）

这些准则在每次编码时自动加载，不需要手动触发：

| 准则 | 核心要求 | 反模式 |
|------|---------|--------|
| **先思考再编码** | 明确假设，不确定就问 | 默默假设然后偷偷实现 |
| **简洁优先** | 200 行能 50 行解决就重写 | "为了灵活性"加一堆用不到的抽象 |
| **精准改动** | 只碰必须改的 | "顺手改善"一下无关代码 |
| **目标驱动** | 写测试验证成功标准 | "应该没问题了" |

### gstack 安全工具

在编码过程中，gstack 提供三层安全网：

| 工具 | 作用 | 使用场景 |
|------|------|---------|
| `/careful` | 破坏性命令警告 | 操作生产环境时 `rm -rf`、`DROP TABLE` 前弹出确认 |
| `/freeze` | 冻结编辑范围 | 调试时防止 AI 顺手改了无关模块 |
| `/guard` | 完全安全模式 | `/careful` + `/freeze` 的组合，最大安全等级 |

**典型用法：**

```
你: "帮我修一下这个登录 bug"
AI (自动激活 /freeze): 编辑范围锁定在 src/auth/ 目录
AI: 只修改 auth 相关文件，不会碰到 payment/ 或 user/ 模块
```

## ④ 质量门：review → QA → 安全审计

**核心问题：** 代码写完了，但它真的能用吗？

代码写完不是结束，gstack 的三道质量门确保代码在合并前经受住考验：

### 三道质量门

```
代码完成
  │
  ▼
┌──────────────┐
│  /review      │ ← 代码审查：SQL 安全、LLM 信任边界、条件副作用
└──────┬───────┘
       │ pass
       ▼
┌──────────────┐
│  /qa          │ ← QA 测试：自动走查页面、截图、发现 bug → 自动修复 → 再测
└──────┬───────┘
       │ pass
       ▼
┌──────────────┐
│  /cso         │ ← 安全审计：密钥泄露、依赖漏洞、OWASP Top 10
└──────┬───────┘
       │ pass
       ▼
    准备发布
```

### 各工具详解

#### /review — 代码审查

不像人类 code review 只看 diff，gstack 的 review 会检查特定的结构性风险：

- **SQL 安全** — 有没有注入风险？事务边界对不对？
- **LLM 信任边界** — 如果代码处理 LLM 输出，有没有做好清洗？
- **条件副作用** — if 分支里有没有遗漏的 return？资源有没有泄漏？

#### /qa — QA 测试 + 自动修复

这是 gstack 最强的能力之一。它用无头浏览器实际访问你的应用：

```
/qa 启动
  → 打开首页 → 截图 → 检查渲染
  → 点击导航 → 检查路由跳转
  → 填写表单 → 提交 → 检查响应
  → 发现 3 个 bug
  → 逐个修复源码 → 原子提交 → 重新验证
  → 3 个 bug 全部修复 ✓
```

如果只需要报告不需要修复，用 `/qa-only`。

#### /cso — 安全审计

首席安全官级别的审计，覆盖：

- 密钥考古（检查历史提交中的泄露）
- 依赖供应链安全
- CI/CD 流水线安全
- OWASP Top 10
- STRIDE 威胁建模

两种模式：日常（零噪音，8/10 置信度门）和全面（月度深度审计）。

## ⑤ 发布上线：ship → deploy → 监控

**核心问题：** 代码审查通过了，但发布流程本身有风险吗？

gstack 的发布管线把从"代码合并"到"线上验证"的整个过程自动化：

### 发布管线

```
代码审查通过
  │
  ▼
┌──────────────┐
│  /ship        │ 合并基线分支 → 运行测试 → 审查 diff
│               │ 更新版本号 → 更新 CHANGELOG
│               │ 提交 → 推送 → 创建 PR
└──────┬───────┘
       │ PR 创建完成
       ▼
┌──────────────┐
│  /land-and-deploy │ 合并 PR → 等 CI → 部署 → 生产健康检查
└──────┬───────┘
       │ 部署完成
       ▼
┌──────────────┐
│  /canary      │ 持续监控：控制台错误、性能回归、截图对比
└──────┬───────┘
       │ 稳定运行
       ▼
┌──────────────┐
│  /benchmark   │ 建立性能基线：页面加载、Core Web Vitals
└──────┬───────┘
       │
       ▼
    发布完成 ✓
```

### 关键设计

- **/ship 不直接 push** — 它创建 PR，让你在合并前还有最后一道人工审视
- **/land-and-deploy 承接 /ship** — 两个命令分工明确：一个管打包，一个管上线
- **/canary 是事后保险** — 部署后自动监控，发现问题立即告警
- **/benchmark 防性能退化** — 每次 PR 自动对比基线，加载时间慢了就拦住

## ⑥ 收尾复盘：文档 + 回顾 + 经验沉淀

**核心问题：** 发布完了就结束了吗？

发布不是终点。gstack 的收尾阶段确保知识不随会话消亡：

### 三步收尾

| 工具 | 作用 | 产出 |
|------|------|------|
| `/document-release` | 同步所有文档 | README、ARCHITECTURE、CHANGELOG 更新 |
| `/retro` | 周工程回顾 | 工作模式分析、贡献分解、代码质量趋势 |
| `/learn` | 跨会话经验记录 | `learnings.jsonl` 持久化，下次会话自动加载 |

### 经验回路

`/learn` 是闭环的关键 — 它把这次会话中的成功模式和踩坑记录写入持久文件。下次启动新会话时，gstack 自动加载这些 learnings：

```
本次会话: "原来 Twikoo 云函数部署需要先配置环境变量"
    ↓ /learn 记录
下次会话: [自动加载] "Recent learnings: Twikoo 云函数需先配环境变量"
    ↓ 避免重复踩坑
```

假设你要给博客加一个 RSS 订阅功能：

```
你: "我想给博客加 RSS 订阅"

  → RSS 要包含全文还是摘要？
  → 需要哪些 feed 格式？RSS 2.0？Atom？JSON Feed？
  → 图片怎么处理？内联还是 enclosure？

  [3 轮对话后]
  → 方案 A: Astro 内置 rss 集成（推荐，零依赖）
  → 方案 B: 手写 XML 模板（完全控制但维护麻烦)
  → 方案 C: 第三方 feed 服务（最简单但有外部依赖)

你: "选 A"
AI: [写入 docs/superpowers/specs/2026-05-10-rss-feed.md]
  → 请确认 spec，确认后我开始实现
```

### 第二步：autoplan 审查（5 分钟）

```
你: "确认了，review 一下方案"
AI: [启动 /autoplan]
  → CEO: "RSS 是标准功能，范围合理，不需要扩展"
  → Eng: "注意 feed 大小，超过 50 篇文章要截断"
  → Design: "订阅按钮放在导航栏，用 RSS 图标"
  → DX: "确保 /feed.xml 和 /rss.xml 都能访问"
  → [审批门] 无边界决策，方案通过
```

### 第三步：编码实现（15 分钟）

```
你: "开始实现吧"
AI: [Karpathy 准则自动生效]
  → 只修改 2 个文件：新增 rss.xml.ts，修改 config.ts
  → 不动其他模块
  → 每个改动直接对应 spec 中的需求
```

### 第四步：质量门（10 分钟）

```
AI: [代码完成，自动进入质量门]
  → /review: "feed 生成逻辑正确，无安全问题"
  → /qa: "访问 /rss.xml 正确返回 XML，验证 3 篇文章的标题和链接"
  → /cso: "无密钥泄露，无依赖漏洞"
  → 质量门全通过 ✓
```

### 第五步：发布（5 分钟）

```
你: "上线"
AI: [启动 /ship]
  → 更新 CHANGELOG → 提交 → 推送 → 创建 PR

你: [在 GitHub 上确认 PR]
AI: [启动 /land-and-deploy]
  → 合并 → CI 通过 → 部署 → 健康检查通过

AI: [启动 /canary]
  → /rss.xml 返回 200 ✓
  → 无控制台错误 ✓
  → 性能无回归 ✓
```

### 第六步：收尾（2 分钟）

```
AI: [启动 /document-release]
  → README 新增 RSS 订阅说明

AI: [启动 /learn]
  → 记录: "Astro RSS 集成需注意 feed 大小截断"
```

**总计约 47 分钟** — 从想法到上线，带完整审查和文档。

## 闭环的核心理念

```
Superpowers 控制 "做什么"  ──→  gstack 控制 "怎么做对"
     │                              │
     │  brainstorming               │  autoplan: 方案审查
     │  防止 AI 方向跑偏             │  review/qa/cso: 代码审查
     │  把模糊想法变 spec            │  ship/deploy: 发布安全
     │                              │  retro/learn: 经验闭环
     │                              │
     └──────── 想法 ────────────────┘
                    │
                    ▼
              可追溯的产出物
         (spec → commit → changelog)
```

**Superpowers 解决的问题：** AI 不会说"不"。你给一个模糊的需求，它就敢写一堆代码。brainstorming 强制在写代码前想清楚。

**gstack 解决的问题：** 代码写完了但没人审。review 只看 diff 不跑代码，QA 跑了但不修。gstack 把审查、测试、修复、发布、监控串成一条自动管线。

**两者配合的魔法：** brainstorming 产出的 spec 是 gstack 审查的输入。没有 spec，autoplan 无从审起。有了 spec，gstack 的每一层审查都有据可依。

这就是 AI 编程的完美闭环 — **不是让 AI 写得更快，而是让 AI 写得更对。**
